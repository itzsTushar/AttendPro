# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `app/main.py` — `health()` function | The endpoint always returned `200 OK` without checking whether MongoDB was available. This violated the readiness probe requirement. | first we noticed from `openaiapi.yaml` then fucntion shoulde behave like this then we check to Stop MongoDB or configure an invalid connection, then call `GET /health`. The original implementation still returned `200` instead of `503`. | Added `client.admin.command("ping")` to verify MongoDB connectivity. The endpoint returns `{"status": "ok"}` when the ping succeeds and raises an HTTP `503 Service Unavailable` exception when it fails. |
| 2 | `app/main.py` — `create_employee()` | Checking for an existing employee before insertion is vulnerable to concurrent requests. Duplicate-key errors were not handled, equal shift times were not rejected, and `created_at` used a potentially timezone-naive timestamp. | Send concurrent POST requests with the same `emp_code`; verify exactly one returns `201` and the others return `409`. Submit equal `shift_start` and `shift_end` values and expect `422`. | Enforce uniqueness with a MongoDB unique index, catch `DuplicateKeyError`, validate that shift times differ, and use a UTC-aware timestamp for `created_at`. |
| 3 | `app/main.py` — `list_employees()` | The pagination offset was incorrect, causing the first page to be skipped. The total count ignored the department filter, results were not sorted by `emp_code` ascending, and page parameters lacked the required validation. | Request `GET /employees?page=1&page_size=20` and verify the first 20 employees are returned. Filter by department and check that `total` counts only matching employees. Verify that results are sorted by `emp_code` ascending. Try `page=0` or `page_size=101` and expect HTTP `422`. | Changed the offset to `(page - 1) * page_size`, used `count_documents(q)` for the filtered total, added ascending sorting by `emp_code`, and validated `page >= 1` and `1 <= page_size <= 100`, with defaults of 1 and 20 respectively. |
| 4 | `app/main.py` — `punch_in()` | Unknown employees were not handled explicitly; timestamps relied on the server timezone; attendance dates did not account for overnight shifts; lateness could use the wrong shift date; and check-then-insert was vulnerable to concurrent duplicate requests. | Test an unknown `emp_code` and expect `404`. Submit simultaneous punch-ins for the same employee and attendance date and expect exactly one `201` and the others `409`. Test an overnight shift after midnight and verify the attendance date. Check that invalid statuses return `422`. | Added employee and status validation, explicit UTC-to-IST conversion, whole-second timestamp precision, overnight attendance-date resolution, lateness calculation against the correct shift date, and `DuplicateKeyError` handling backed by a unique compound index on `(emp_code, date)`. |
| 5 | `list_attendance()` — `GET /attendance` | Loads all matching records into memory and sorts them in Python; sorting omits the secondary `emp_code` ascending order; `total` is calculated after loading all records; pagination and date-range validation are missing. | Test with around 100,000 records to observe unnecessary memory usage; check ordering when multiple employees share a date; use `page=0`, `page_size=101`, invalid dates, or `date_from > date_to`. | Move filtering, sorting, pagination, and limiting into MongoDB; use `count_documents(q)` for the filtered total; sort by `date` descending and `emp_code` ascending; validate pagination and date ranges; add indexes to support the query and verify performance with `explain("executionStats")`. |
